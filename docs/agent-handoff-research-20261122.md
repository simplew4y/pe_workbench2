## 4. 已确认缺陷与代码原因

下列代码路径均相对 `/home/simpleway/pe_workbench2`；行号以 `c19aa31` 为准。

### P1-01：删去证据后，结论或标题仍被保留

**证据：** T01-R3 最终正文中反驳证据被替换为待核句，但结尾仍称“‘无经营改善’的结论被2024年的毛利和经营利润数据推翻”。T04-R1 保留“长鑫自己就是价格下跌的一个原因”及强断言标题，邻近正文却说证据不足。

**代码中已确认的局限：**

- `server/agent/answer-delivery.mjs:765` 的 `researchPortion` 主要按字符串命中、句子重叠和 `dependent()` 连接词判断依赖；不能识别“判断：反方被推翻”等跨段语义依赖。
- `:773` 的依赖规则依赖“因此/所以/这说明”等词；先出现的总论不会因后面证据被删而被回溯处理。
- 标题分支只检查标题自身是否命中 finding，并重置 `sectionRejected`，没有确认标题所依赖的正文是否仍存在。
- `lib/research-delivery.mjs:230` 的 `applyOpenFindings` 与 `researchPortion` 是不同处理层；前者已把问题句换成模板，后者更难恢复原始主张关系。

**后续方向：** 在裁剪/改写前保留主张与证据、推导及结论的关联；对受影响段落及其摘要/标题一起处理。缺乏模型额度时也要保证确定性降级不会留下比保留证据更强的结论，而不是仅扩大连接词正则。

**验收：** 同一错误前提分别放在摘要之后、跨标题、表格、列表和反方论证中；移除后不得残留依赖结论，同时保留真正独立的分析。必须覆盖 402 发生在修订过程中的回退路径。

### P1-02：失败的计算已完全重算，历史失败仍让整题 partial

**本次整理中新核实，比旧问题记录更明确。** T02-R1 的失败调用只有两项：

```json
{
  "toolCallId": "call_00_5ERxqI8uQBsRenKlBITv6575",
  "expressions": [
    {"name":"储能毛利额","expression":"249.5916612781-158.0085329138","outputUnit":"亿元"},
    {"name":"逆变器毛利额","expression":"291.27038840\u00ad90-201.2800552330","outputUnit":"亿元"}
  ]
}
```

随后成功调用 `call_00_ET_F59mKWQdccC6YGW5GPzi1762`，完整重算同两项；第二式去掉 U+00AD，结果分别为 `91.5831283643`、`89.990333176` 亿元。最终 reason 仍是“工具 calc 执行失败”，正文说“一项派生数值计算未成功”。**旧文档中“是否全部替代仍待核对”的判断已被此证据更新：这个失败批次的两项均有成功替代。**

**代码原因：**

1. `server/agent/post-answer.mjs:500` 用 `toolName + JSON.stringify(args)` 对调用去重。修复输入字符后 args 已变化，旧失败不会被新成功覆盖。
2. `lib/research-audit.mjs:254` 仅在整体 `parsed.ok` 时采纳 `resolvedToolFailures`。
3. `lib/research-delivery.mjs:382`、`:457` 又把恢复回执绑定整体审校通过、草稿未变化、无 openFindings。
4. `server/agent/post-answer.mjs:504` 只在 `semanticReviewed` 时使用恢复回执。于是无关的阈值/引用问题也可能使已经解决的算术失败重新成为整题阻断。

**后续方向：** 将“某个工具输出已被替代”的事实与“全文研究审校通过”分离，按输出语义、来源/输入、公式、单位、期间建立可验证替代关系。不要按工具名全局清失败，也不要要求成功参数字符串与失败参数完全一样。

消除这一项错误归因不代表该题就应该 completed：其余业务口径、来源或推理问题仍需独立判断，不能把“已恢复计算”当作“整篇研究通过”。

**验收：** 完整替代、不完整替代、不同单位/期间的伪替代、另一段仍有研究问题、402 后保留已验证结果。用户提示应点名真正未解决的指标，不能只说“有一项”。

### P1-03：语义审校自己算错，把正确的单位换算当成十倍错误

**本次整理中新确认。** T02 的 `research-audit.jsonl` 在 `2026-11-21T16:39:14.566Z`（UTC）把“249.59亿元÷28GWh≈0.891元/Wh”判为疑似十倍错误，理由称：

> 249.59亿元=2.496×10^11元……结果约8.91元/Wh。

但确定性复算为：

```text
249.59 × 10^8 / (28 × 10^9) = 0.891392857142857… 元/Wh
```

审校把金额换算多乘了 10；其“280亿Wh=280GWh”的说明也错误。**该段真实存在业务口径问题，但不能据此把正确算术说成十倍错误。** 最终正文保留了约 0.891，不代表错误审校没有消耗修订或扰乱过程。

**原因与定位：** `lib/research-audit.mjs` 的 `numeric_units` 语义意见直接参与 `issues`；虽有确定性检查合并，当前没有可靠机制裁决“审校的手算理由”与成功的算术及单位证明之间的冲突。还需追踪此具体 issue 在 guard 中导致的后续动作，不能把每次重写耗费都归于这一项。

**后续方向：** 算术与量纲争议交给确定性证明；模型审校负责提出需要复核的输入语义、业务范围和证据问题。禁止审校靠另一段自由手算推翻已核验算术，也不能让算术正确替业务口径背书。

**验收：** 模拟错误审校提出十倍、百分数/小数混淆；正确换算应保留，真实输入范围不一致仍阻断；无需调用真实模型。

### P1-04：算式字符污染与批量失败隔离不足

**观察：** 上述原始参数中确有 U+00AD 软连字符，错误为 `calc 失败：多余算式符号：­`。它可能来自 PDF 文本或生成过程，**仅凭现有记录不能确定最初由哪一层引入**；不要把“来自 PDF”当成已经追踪完毕的根因。

`lib/calc-tool.mjs:410` 起逐项计算，外层统一 try/catch；第二项失败会让已计算的第一项也无法以成功结果交付。另 R6 记录出现非整数幂错误：`:143` 的 `power()` 只特判平方根，其余进入 `integer()`；`^(1/4)`、`^0.25` 不支持。

**后续方向：** 对已知排版控制符做保守规范化并记录原式/规范式；不可把所有未知字符静默删除。批量应返回逐项成功/错误及各自证据，随后一起更新事实保存、审校与失败恢复消费者，不能只更改返回 JSON。数学能力若扩展，需约定误差、定义域、复杂度上限；否则明确支持范围并避免重复尝试。

### P1-05：研究假设、期间、业务范围与因果解释仍会混用

**真实例子：**

- T01-R2 先说期限为 2026 财年，后把公司 2025 年回购≥800亿港元、股息≥4.50港元的计划用于 2026 年，并称“不是本框架自设阈值”。向下一年外推应成为研究假设，而非继续视为原始指引。
- T02-R1 用“光伏逆变器等电力电子转换设备”合并收入除以逆变器发货量，解释为单价下降；又将毛利率下降称为降价的直接代价，未排除范围、确认时点、结构和成本影响。
- T03-R2 的可证伪命题形式完整，但预测头部 IP 下一年收入回落没有充分解释依据。
- T05-R2 “直销不形成预收”过于绝对；把预收增加与已经发货的渠道库存转移直接联系，未拆开收款、履约和收入确认。

**定位与判断：** `lib/financial-evidence.mjs:517` 的 claimDimensions、`:555` 附近的身份比较及 `lib/financial-source-identity.mjs` 已改善产品/指标识别，但自由正文中的跨年度假设继承、复合分母、因果强度依然主要依赖语义审校。不能断言是某个正则单独造成以上全部错误。

**后续方向：** 把事实期间、适用预测期间、披露/假设身份、收入/出货范围和推导前提作为可继承的结构信息；检验事实到假设的转换。审校能指出替代解释还不够，最终正文必须实际服从该边界。

### P2-01：来源有时被找到，却没有可靠地交付给用户

T03-R1 最终只有“年报 p.xx”，无官方链接；T05-R1 用未展开的“茅报/五报”缩写；T02-R1 分产品数据依赖转载全文，官方全文定位不完整。这三类分别是**引用交付缺失、缩写无法解析、取证层级不足**，不要混成“可信源数量少”。

优先检查最终引用组装、草稿压缩/改写与来源注册表的映射。关键数字应能从最终正文抵达实际支持该主张的文档和表/页；不能用官方摘要链接替转载全文数字背书，也不必为解决这一点重新把 Excel 单元格地址堆回正文。

### P2-02：篇幅目标被当软约束，多次重写仍冗长

`lib/answer-length.mjs:5–10` 能识别“限600字”，但 strict 判定不包含单独“限”，会生成“需要时可以略超”的提示。它能解释宽松执行的一部分；600 字变成 1200 余字的完整路径还要结合 `post-answer.mjs` 的压缩与回退分支核对。

修复时明确“限/最多/约”的语义，约束正文、引用和附注的统计口径；保留问项、关键条件和必要来源，不要通过硬截字符串留下半句、断表或删除核心证据。

### P2-03：内部修订过程与模板缺口污染正文

T04-R1 出现对“2024年11月”的日期更正，而原题没有该错误；这是对内部草稿的纠错泄漏。正文又反复出现“此项判断证据不足”“此处数值或单位尚需核对”。

`lib/research-delivery.mjs:230` 按 finding 逐个替换固定句；`researchPortion` 再附全局/分节缺口说明。多层处理并不保证最后仍是一篇能读的研究答复。应将内部修订历史隔离，并按对象合并说明“什么未知、为何影响哪个判断、已有结论适用到哪里”。

### P2-04：计算结果的数值与单位标签可能不一致

T02-R1 成功工具结果把 `705.148/778.57 = 0.905696340727` 标为 `%`，另把 `-0.068508397644` 标为单价变动的 `%`。最终正文使用约 90.6%、下降 6.85%，数值转换本身合理，但与工具原始标签不一致，审校已因此提出异议。

`lib/calc-tool.mjs` 对没有来源 bindings、没有 fromUnit/toUnit 的普通计算允许用 outputUnit 标注结果；它不能仅凭标签判定用户意图是比例小数还是百分数。因此不能简单“见 % 就乘 100”。需使百分数/小数转换显式化，并让工具、事实记录和最终正文共享同一类型约定；补 0.9 decimal 与 90% 的双向等价、0.9% 不等价等反例。此问题与 P1-03 不同：这里工具元数据确有歧义，那里是审校自己发生十倍换算错误。
